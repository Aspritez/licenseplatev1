===========================================================
PROJECT REQUIREMENTS (v2 - ปรับปรุงสำหรับ Present/เดโม)
ระบบตรวจจับและอ่านป้ายทะเบียนรถ (Thai License Plate Detection & OCR Web App)
===========================================================

หมายเหตุ: เอกสารฉบับนี้ปรับปรุงจากฉบับเดิม โดยปรับ scope ให้เหมาะกับ
การใช้งานแบบ "present วิธีการใช้งาน" (ไม่ต้องเก็บข้อมูลถาวร ไม่ใช่ระบบ
production ที่มีผู้ใช้ต่อเนื่อง) จุดที่เปลี่ยนจากฉบับเดิมจะมีหมายเหตุ
กำกับไว้ในแต่ละหัวข้อ

1. ภาพรวมโปรเจกต์ (Project Overview)
-----------------------------------------------------------
พัฒนาเว็บแอปพลิเคชันที่ให้ผู้ใช้อัปโหลดรูปภาพรถยนต์ จากนั้นระบบจะทำการ
ตรวจจับและตัดเฉพาะส่วนป้ายทะเบียนรถ (ภาษาไทย) ออกมาด้วยเทคนิค Computer
Vision แบบดั้งเดิม (Classical CV, ไม่ใช้ Deep Learning ในขั้นตอนตัดภาพ)
แล้วนำภาพที่ตัด/ปรับมุมมองตรงแล้วไปประมวลผลด้วย OCR เพื่ออ่านข้อความบน
ป้ายทะเบียน พร้อมแสดงผลลัพธ์อย่างครบถ้วนทั้งก่อนและหลังการประมวลผล
ระบบทำงานแบบ stateless เต็มรูปแบบ ไม่มีการเก็บข้อมูลถาวรฝั่งเซิร์ฟเวอร์

2. Functional Requirements (ความต้องการด้านฟังก์ชัน)
-----------------------------------------------------------
2.1 Upload รูปภาพ
    - ผู้ใช้สามารถอัปโหลดรูปภาพ (jpg, png ฯลฯ) เข้าสู่ระบบผ่านหน้าเว็บได้
    - รองรับการแสดงตัวอย่างภาพก่อนกดประมวลผล
    - [ไม่เปลี่ยน] ภาพที่อัปโหลดถูกเก็บเป็น temp file/in-memory ระหว่าง
      request เท่านั้น ไม่มีการบันทึกลง disk ถาวรหรือฐานข้อมูล

2.2 การตรวจจับและตัดป้ายทะเบียน (License Plate Detection & Cropping)
    ใช้เทคนิค Computer Vision แบบดั้งเดิม (ไม่ใช้ Deep Learning) ตาม
    pipeline ดังนี้ โดยกำหนดอัลกอริทึมตายตัวในระบบอัตโนมัติ (ไม่เปิดให้
    ผู้ใช้ทั่วไปเลือกอัลกอริทึมเอง เพื่อความง่ายในการใช้งาน แต่ออกแบบโค้ด
    แบบ modular ไว้ เผื่อขยายเป็น "Advanced/Dev Mode" ในอนาคต):

    a) Preprocessing
       - แปลงเป็น Grayscale -> Gaussian Blur -> ปรับ contrast ด้วย
         CLAHE หรือ Adaptive Threshold เพื่อให้ขอบป้ายทะเบียนชัดเจนขึ้น

    b) Edge Detection
       - ใช้ Canny Edge Detection หาขอบวัตถุในภาพ

    c) Contour Detection
       - ใช้ cv2.findContours หา contour ทั้งหมด แล้วกรองด้วยเงื่อนไข
         พื้นที่ (area) และสัดส่วนกว้าง/สูง (aspect ratio) ที่ใกล้เคียง
         ป้ายทะเบียนรถไทย เพื่อคัดเลือก contour ที่น่าจะเป็นป้ายทะเบียน

    d) Corner Detection / Keypoints Extraction (หาจุดมุมทั้ง 4 จุด)
       - ใช้ cv2.approxPolyDP บน contour ที่เลือกได้ เพื่อลดจุดเหลือ
         4 จุดมุม (Quadrilateral Approximation)
       - Refine ตำแหน่งจุดมุมแบบ sub-pixel ด้วย Shi-Tomasi Corner
         Detection (cv2.goodFeaturesToTrack) ในบริเวณใกล้แต่ละมุม
       - เหตุผลที่เลือก Shi-Tomasi แทน Harris/SIFT/SURF/ORB: Shi-Tomasi
         ให้ผลแม่นยำและเสถียรกว่า Harris สำหรับงานหามุมของวัตถุสี่เหลี่ยม
         ส่วน SIFT/SURF/ORB เหมาะกับการจับคู่ (matching) กับภาพอ้างอิง
         ซึ่งไม่จำเป็นในกรณีนี้ เพราะหามุมได้จาก contour ของภาพเดียวอยู่แล้ว

    e) Point Correspondence (การจับคู่พิกัดจุดเป้าหมาย)
       - นำพิกัดจุดมุม 4 จุดที่ตรวจจับได้จากป้ายทะเบียนที่เอียง (เรียงลำดับ
         Top-Left, Top-Right, Bottom-Right, Bottom-Left) มาจับคู่กับ
         พิกัดเป้าหมาย 4 จุดของสี่เหลี่ยมผืนผ้าแนวตรงขนาดมาตรฐาน W x H
         (เช่น 400 x 200 พิกเซล ตามสัดส่วนป้ายทะเบียนไทยจริง)

    f) Homography Calculation
       - ใช้ cv2.getPerspectiveTransform คำนวณเมทริกซ์แปลงพิกัดจาก
         4 คู่จุดโดยตรง (แม่นยำสูงสุดเมื่อมีจุด correspondence พอดี 4 จุด)
       - ไม่ใช้ RANSAC ในขั้นตอนอัตโนมัติหลัก เนื่องจาก RANSAC เหมาะกับ
         กรณีมีจุด correspondence จำนวนมากและมี outlier (เช่นจากการจับคู่
         แบบ feature matching) ซึ่งไม่ใช่กรณีนี้ที่มีแค่ 4 จุดที่ refine
         มาแล้ว อย่างไรก็ตาม ให้เตรียมฟังก์ชัน cv2.findHomography กับ
         cv2.RANSAC ไว้เป็นทางเลือกสำรอง เผื่ออนาคตขยาย pipeline ให้ใช้
         จุดมากกว่า 4 จุดจาก feature matching

    g) Perspective Correction / Warp Perspective
       - ใช้ cv2.warpPerspective แปลงภาพป้ายทะเบียนที่เอียงให้กลับมาเป็น
         ภาพสี่เหลี่ยมผืนผ้าแนวตรงขนาด W x H คงที่ ก่อนส่งเข้ากระบวนการ OCR

2.3 การประมวลผล OCR
    - นำภาพป้ายทะเบียนที่ตัดและปรับมุมมองตรงแล้ว (จาก 2.2) ไปผ่าน
      กระบวนการ OCR เพื่ออ่านข้อความ (ตัวอักษร/ตัวเลขภาษาไทย)
    - แสดงผลลัพธ์ข้อความที่อ่านได้จาก OCR
    - [ไม่เปลี่ยน] ประมวลผลแบบ synchronous ภายใน request เดียว (ไม่ใช้
      background task queue เนื่องจากเวลาในการประมวลผลต่อภาพอยู่ในระดับ
      วินาที และระบบไม่มี concurrent load สูงในบริบทของการ present)

2.4 การแสดงผลลัพธ์ (Result Display)
    ระบบต้องแสดงผลครบทั้งส่วน ได้แก่:
    - ภาพก่อนการประมวลผล (ภาพต้นฉบับที่อัปโหลด)
    - ภาพหลังการประมวลผล (ภาพที่ตัดและปรับมุมมองตรงแล้ว)
    - ผลลัพธ์ข้อความจาก OCR
    - ค่าความแม่นยำ (Accuracy/Confidence Score) ของผลการตรวจจับและ/หรือ OCR
    - [ไม่เปลี่ยน] ผลลัพธ์ทั้งหมดส่งคืนภายใน response เดียว (ภาพ encode
      เป็น base64 ฝังในหน้า HTML) ไม่มีการสร้าง URL ถาวรของไฟล์ผลลัพธ์

2.5 ระบบแก้ไขแบบ Manual (Manual Correction)
    - ในกรณีที่ระบบตรวจจับป้ายทะเบียนผิดพลาด ผู้ใช้ต้องสามารถ:
        * ลากปรับตำแหน่งจุดมุมทั้ง 4 จุด (Corner Points) บนภาพต้นฉบับ
          ด้วยตนเอง ผ่าน interactive canvas บนหน้าเว็บ (ไม่ใช่แค่ลากกรอบ
          สี่เหลี่ยมตรงธรรมดา เพื่อรองรับป้ายที่เอียง/บิดมุมมองได้)
        * เมื่อผู้ใช้ปรับจุดมุมเสร็จ ระบบนำจุดที่ผู้ใช้กำหนดไปผ่านขั้นตอน
          Point Correspondence -> Homography -> Warp Perspective (ตาม
          ข้อ 2.2 e-g) แล้วส่งภาพที่ได้ไปประมวลผล OCR ใหม่อีกครั้ง
    - [ไม่เปลี่ยน] ภาพต้นฉบับระหว่างขั้นตอนแก้ไข manual เก็บไว้ชั่วคราว
      (เช่น ส่งกลับไปมาระหว่าง client-server เป็น base64 หรือเก็บใน
      session ชั่วคราว) ไม่บันทึกลงฐานข้อมูล

3. Non-Functional Requirements (ความต้องการอื่น ๆ)
-----------------------------------------------------------
3.1 UI/UX
    - โทนสีหลักของเว็บไซต์ (Theme): สีน้ำเงิน (Blue) และ สีขาว (White)
    - หน้าจอใช้งานง่าย เข้าใจขั้นตอนการทำงานได้ชัดเจน (upload -> ผลลัพธ์
      -> แก้ไข manual ถ้าจำเป็น)

3.2 ภาษาโปรแกรม (Programming Language)
    - Python (สำหรับส่วนประมวลผลภาพ/Detection/OCR/Backend ทั้งหมด)

3.3 สถาปัตยกรรม (Architecture)
    - [เปลี่ยน] เป็นเว็บแอป monolith เดียว ไม่แยก frontend/backend
      ออกจากกัน (ไม่ทำ SPA + REST API แยก) เนื่องจาก workflow เป็นแบบ
      เส้นตรง (upload -> ผลลัพธ์ -> แก้ manual) ไม่มีความจำเป็นต้องใช้
      สถาปัตยกรรมแบบแยกส่วน
    - [เปลี่ยน] ไม่มีฐานข้อมูล (No Database) ระบบไม่เก็บประวัติการ
      อัปโหลด/ผลลัพธ์ใดๆ ทั้งสิ้น ทุกอย่างประมวลผลและส่งคืนภายใน
      request-response cycle เดียว

3.4 การ Deploy
    - ไม่จำกัดต้องขึ้น Vercel (เปลี่ยนจากเดิม) — เลือกแพลตฟอร์มที่รองรับ
      persistent server และไลบรารี Computer Vision ได้เต็มที่แทน
    - [เปลี่ยน] จำกัดงบประมาณเป็น Free Tier เท่านั้น — ต้องเลือกแพลตฟอร์ม
      ที่มี free tier ถาวรและรองรับ Docker (ดูรายละเอียดในข้อ 4)

4. เทคโนโลยีที่แนะนำ (Suggested Tech Stack) [ปรับปรุงใหม่]
-----------------------------------------------------------
- Backend Framework: Flask (เปลี่ยนจาก Django)
    * เดิมแนะนำ Django เพราะมี Admin Panel + ORM สำหรับเก็บประวัติ
      อัปโหลด/ผลลัพธ์ แต่เมื่อตัด requirement เรื่องฐานข้อมูลออก
      จุดแข็งเหล่านั้นไม่ถูกใช้งานอีกต่อไป
    * Flask เบากว่า ติดตั้ง/ดูแลง่ายกว่าเมื่อไม่มี DB, ORM, migration
      ให้จัดการ เหมาะกับ scope ที่เหลือคือ "รับไฟล์ -> ประมวลผล ->
      render ผลลัพธ์" ล้วนๆ
    * มี Jinja2 template engine ในตัว ใช้ render หน้า HTML ที่ฝัง
      canvas สำหรับ manual correction ได้ทันทีโดยไม่ต้องติดตั้งเพิ่ม

- Computer Vision: OpenCV (opencv-python)
    * ใช้ทำ pipeline ทั้งหมดตามข้อ 2.2 (Edge Detection, Contour,
      Corner Detection, Homography, Warp Perspective)

- OCR Engine: Tesseract OCR (pytesseract) พร้อม language pack "tha"
    * รองรับภาษาไทย ติดตั้งง่าย ไม่ต้องพึ่ง GPU
    * ทางเลือกอื่น (แม่นยำกว่าแต่หนักกว่าและใช้ Deep Learning ภายใน):
      EasyOCR, PaddleOCR — ใช้ได้เฉพาะขั้นตอน OCR เท่านั้น ไม่กระทบกับ
      ข้อกำหนดที่ต้องการให้ขั้นตอน "ตัดภาพ/หาป้ายทะเบียน" เป็น Classical
      CV ล้วน

- Frontend สำหรับวาด/ปรับจุดมุมแบบ Manual: Fabric.js หรือ Konva.js
    * ฝังในหน้า Flask (Jinja2) Template โดยตรง ไม่จำเป็นต้องใช้ React
      แบบเต็มรูปแบบ SPA เพราะ Canvas library เพียงพอสำหรับ interactive
      corner-dragging และเบากว่า ดูแลง่ายกว่าสำหรับผู้พัฒนาคนเดียว

- Background Task Queue: [ตัดออก] ไม่ใช้ Celery/Redis
    * เดิมพิจารณาใช้เพื่อไม่ให้ CPU-heavy task (OpenCV/Tesseract) block
      request แต่เนื่องจากงบจำกัดเป็น free tier (ไม่มี background
      worker ฟรี) และเวลาในการประมวลผลต่อภาพอยู่ในระดับวินาที จึงตัด
      ออกและประมวลผลแบบ synchronous แทน โดยใส่ loading indicator
      ฝั่ง frontend ระหว่างรอผล

- Database: [ตัดออก] ไม่มีฐานข้อมูล
    * เดิมพิจารณาใช้ PostgreSQL ผ่าน Django ORM สำหรับเก็บประวัติ แต่
      เนื่องจากไม่ต้องการเก็บข้อมูลถาวร จึงตัดออกทั้งหมด ลด dependency
      และหลีกเลี่ยงปัญหา free-tier database ที่ถูกลบอัตโนมัติหลัง
      ระยะเวลาที่กำหนด

- Deployment: Render (Free Tier)
    * รองรับ persistent server เต็มรูปแบบ ไม่ติด limit แบบ Serverless
      (execution timeout, package size) เหมือน Vercel
    * ติดตั้ง OpenCV และ Tesseract ผ่าน Docker ได้ตรงไปตรงมา
    * มี Free Tier ถาวรสำหรับ web service เดียว (ไม่ต้องผูกบัตรเครดิต)
      เหมาะกับ scope ที่เหลือ (ไม่มี DB, ไม่มี background worker ให้
      ต้องเสียเงินเพิ่ม)
    * ข้อควรรู้: web service บน free tier จะ sleep หลังไม่มี traffic
      15 นาที และมี cold start 30-60 วินาทีในการเรียกครั้งถัดไป —
      แนะนำเปิดเว็บทิ้งไว้ล่วงหน้า 1-2 นาทีก่อน present เพื่อ "ปลุก"
      service ให้พร้อมใช้งาน

5. Workflow สรุป (Summary Flow)
-----------------------------------------------------------
1) ผู้ใช้ upload ภาพรถยนต์ (ไม่มีการบันทึกไฟล์ถาวร)
2) ระบบประมวลผลอัตโนมัติแบบ synchronous ภายใน request เดียว:
   Preprocessing -> Edge Detection -> Contour Detection ->
   Corner Detection (Shi-Tomasi) -> Point Correspondence ->
   Homography (getPerspectiveTransform) -> Warp Perspective
3) ระบบส่งภาพที่ตัดและปรับมุมมองตรงแล้วไปประมวลผล OCR (Tesseract, tha)
4) แสดงผล: ภาพก่อนประมวลผล / ภาพหลังประมวลผล / ผลลัพธ์ OCR / ค่าความแม่นยำ
   (ส่งคืนทั้งหมดใน response เดียว ไม่มี URL ถาวร)
5) หากผลลัพธ์การตรวจจับผิดพลาด ผู้ใช้ลากปรับจุดมุม 4 จุดเองบน canvas
   (manual) แล้วระบบคำนวณ Homography + Warp + OCR ใหม่ให้อัตโนมัติ
   ภายใน request เดียวกัน (ไม่มีการบันทึกภาพต้นฉบับถาวรระหว่างขั้นตอนนี้)

===========================================================
สรุปการเปลี่ยนแปลงจากฉบับเดิม
===========================================================
1. Backend: Django -> Flask (ไม่มี DB ให้ใช้ ORM/Admin จึงไม่จำเป็น)
2. สถาปัตยกรรม: ยืนยันเป็น Monolith เดียว ไม่แยก frontend/backend
3. ตัด Database ออกทั้งหมด (ไม่เก็บประวัติ/ผลลัพธ์ถาวร)
4. ตัด Celery/Redis (background task queue) ออก ใช้ synchronous
   processing แทน เพราะ free tier ไม่รองรับ worker ฟรี และงานเบา
   พอที่จะรันใน request เดียวได้
5. Deployment: ปรับเป็น Render Free Tier เท่านั้น (Fly.io ไม่มี free
   tier แล้ว, Railway ให้เครดิตฟรีจำกัดใช้ได้ไม่นาน)
===========================================================
